# Technical design
**Version:** 0.3 · **Updated:** 22 October 2026 · **Status:** proposed algorithms, Mollie selected and Cloudflare app hosting requested; no delivered application code

Cloudflare deployment needs runtime qualification alongside these algorithms; see [Cloudflare versus Render](18-cloudflare-vs-render.md), [the backend assessment](19-backend-options.md) and [ADR 0008](../docs/adr/0008-use-typescript-for-cloudflare-backend.md). TypeScript on Workers is selected following the founder's delegated choice. Bounded scheduled handlers use the same PostgreSQL inbox/outbox, with leases and resumable progress. Request lifetime or `waitUntil()` is never the sole durable execution mechanism for payments, refunds, alerts or erasure. Keep the domain transactions, uniqueness and authorization rules below.

The selected TypeScript/Hono Workers backend uses Hyperdrive and paid Render PostgreSQL in Frankfurt, with query caching disabled on the application binding. Financial and consent decisions read current PostgreSQL state through an explicit transaction-scoped SQL connection; do not rely on session-level database state surviving pooled requests. Hyperdrive connects to Render's external TLS hostname with server-only credentials and reviewed source-IP restrictions, not its Render-private URL. React Router framework mode with React/Vite/SSR is confirmed for the frontend. Better Auth is confirmed for company/staff accounts. Qualify exact Hono/React Router/Better Auth versions and driver/media dependencies in the selected runtime. This is a design update, not a completed compatibility check; see [ADR 0009](../docs/adr/0009-use-render-postgresql-in-frankfurt.md).

Better Auth provides a [Drizzle adapter](https://better-auth.com/docs/adapters/drizzle). The tooling choice is confirmed; dependency installation and runtime qualification remain work.

Use typed schema/queries and [generated SQL migration files](https://orm.drizzle.team/docs/drizzle-kit-generate), with reviewed SQL for database constraints, indexes and critical locking/claim statements. The ORM does not replace publication/refund uniqueness, explicit lock ordering, current authorization or job lease/idempotency rules. Bind every domain transaction to one connection for its duration; keep Hyperdrive application query caching disabled and do not assume persistent session state. Qualify the exact pg/Drizzle/Better Auth adapter versions, Workers compatibility settings, connection cleanup and rollback/concurrency behavior together. Auth adapter operations need their own verified transaction/atomicity behavior rather than an assumption that an outer application transaction covers them. Apply reviewed migrations through a separate least-privileged deployment/migration path, outside request/Cron startup; no schema-push-on-request behavior. ## 1. Invariants
1. Client platform fee is zero. Only the company pays the confirmed €1 VAT-inclusive first-publication fee through individual Mollie-hosted checkout; bundles/wallets/subscriptions are deferred until after MVP, while merchant/method activation remains separate launch work.
2. One company/task response; at most one retained successful publication fee for it. Retries/edits/withdrawals do not create another charge.
3. No response is visible without a verified payment or a separately approved, auditable promotion (none enabled in MVP).
4. Paid but ineligible/unpublished attempts must reach a tracked full-refund outcome; an ambiguous external result cannot be retried blindly.
5. Company can read safe tasks free, never rivals' responses or counts. Client job owner sees all its eligible submitted offers.
6. Client contact is disclosed only through current explicit mode/field permission plus an eligible published response on an OPEN task.
7. Every task read/send/write/download checks delete_at; a late worker does not extend access.
8. Photos/text/offers/contact grants/guest access and derived task location are purged by policy; financial records contain no unnecessary task/client content.
9. No private PWA cache or queued financial mutation.

## 2. Guest publishing and company/staff accounts
A guest provides email for management, not a compulsory account. Use a random high-entropy one-use token; store only its hash, purpose, job ID and short expiry (proposed 15 minutes). Resend is rate limited and generic; no email/job enumeration. Exchange token via a controlled POST into an HttpOnly/Secure/SameSite job-scoped session; remove token from visible URL and exclude query/fragment credentials from logs/analytics/referrers. Do not turn email into a permanent privileged link.

The founder confirmed email verification before publication, task-scoped short-lived email access and fresh-link recovery without registration; optional client accounts, multi-task account dashboards and task linking are deferred until after MVP. See [ADR 0002](../docs/adr/0002-confirm-email-for-guest-task-ownership.md). Phone verification is not required for the confirmed default client-initiated mode. Any future client-account linking must prove task ownership rather than trust a caller-supplied email. Session revocation, deletion and account switch must work across open browser contexts. Company/staff accounts stay in scope; company accounts use separate server-derived company ownership and confer no automatic guest-task access. An email-confirmed company is not certified.

Better Auth is selected for company/staff authentication, with account/session records in Render PostgreSQL; see [ADR 0011](../docs/adr/0011-use-better-auth-for-company-and-staff-accounts.md). Qualify its database adapter through Hyperdrive, cryptographic operations, SSR/API cookie propagation and immediate revocation in Workers. Required staff MFA must hold across every enabled sign-in and recovery path; enabling a library plugin alone does not establish that policy. Company verified-email/password and staff invite-only password/TOTP/recovery-code policies are confirmed; implementation and operating recovery procedures remain to qualify.

The founder confirmed verified email plus password for company sign-in, with email verification and password recovery. Require verification before company access; use the selected library for credential handling, verification and reset flows. Qualify one-use/expiry checks, generic recovery responses, rate limits and current company authorization across browser/PWA contexts. Passwordless company login is not selected, and guest task-scoped access remains separate. See [Better Auth email/password](https://better-auth.com/docs/authentication/email-password).

The founder confirmed invite-only staff email/password sign-in with mandatory authenticator-app TOTP and one-use recovery codes. Enforce completed MFA before staff privileges, including on existing company sessions when a staff role is granted; password reset must not remove the MFA requirement. Qualify enrollment, atomic recovery-code consumption, revocation and alternate-route checks using [Better Auth 2FA](https://better-auth.com/docs/plugins/2fa). Document initial privileged-user provisioning and the operating process for a staff member who loses both their authenticator and recovery codes before beta; no email-only MFA bypass is approved.

## 3. Task and response authorization
A server-only DAL returns different DTOs for company task view, company own response, client offer list, contact disclosure and finance. Never serialize a raw ORM job/response relation and hide fields in React. Personal HTML, serialized route data and API responses are private/no-store, excluded from CDN/service-worker caches.

Company task view omits full postcode, client name/email/phone, management identifiers and all bidder metadata. Client listing query uses the owner principal/job ID and pagination without leaking cursor authority. Other companies' IDs/offer counts return no data, including aggregates, errors, exports and attachment parents.

A callback-contact read requires active account + PUBLISHED own response with valid retained fee + OPEN, unexpired, non-held job + current ALLOW_RESPONDERS grant for exactly the returned fields. The founder confirmed the audience is every eligible published responder, without per-company selection; see [ADR 0003](../docs/adr/0003-client-controlled-responder-contact.md). Default CLIENT_INITIATED returns no client contact even after payment. Closing, withdrawal or revocation immediately prevents new disclosure.

Confirmed close/reopen policy: preserve offers, paid fees and original expiry; reopening a voluntary closure requires fresh callback opt-in and never revives canceled attempts. See [ADR 0006](../docs/adr/0006-reopen-without-renewing-fees-or-consent.md). Proposed persistence: store a monotonic job `publication_generation` and snapshot it on payment attempts. Under the job lock, closure increments this generation, disables active callback permission with a new consent version, and queues payment reconciliation. Reopening never rolls the generation back and starts in CLIENT_INITIATED with no active shared fields. Check both generation and material revision during fulfillment: current OPEN alone is insufficient after a close/reopen cycle. The same durable invalidation mechanism applies to other transitions that cancel publication eligibility; a client cannot clear a safety hold through reopening.

Confirmed published-offer withdrawal is final for that company/task in MVP. Under job -> response lock order, mark WITHDRAWN without deleting the unique response/fulfillment relationship. The client projection returns company name and withdrawn marker only, with no offer text, website or company contact fields; callback reads fail. Reject editing-to-republish, restoration and new payment attempts for this terminal response, including draft creation/upsert and task reopening. Historical payment replays may recover the owned fee/receipt reference but must show current withdrawal state and cannot change it. The original fee remains without automatic refund; unpublished failed/refunded attempts are a separate lifecycle.

Store/render descriptions and introductions as plain text or a strictly sanitized subset, escape outputs, parameterize queries and reject unknown mutation fields. Validate contact/website URL schemes; never execute HTML/JavaScript supplied in a rough bid. External website links use safe browser attributes and do not trigger automatic server-side preview fetching of arbitrary URLs. Apply CSP, CSRF/origin checks, request size/rate bounds and per-owner media authorization. No SVG/HTML/executable upload types.

Photo storage is confirmed as private Cloudflare R2 with explicit EU jurisdiction. Configure the bucket and Worker binding for the eu jurisdiction, leave r2.dev and public bucket custom-domain access disabled, and serve sanitized variants through application-authorized Worker endpoints. Check current task/account permissions and expiry on every read; possession of an object key or previously issued URL must not bypass revocation. Originals/quarantine are not ordinary download endpoints. The confirmed upload limits are six photos per task and 10 MB per file. Qualify the sanitization path, supported formats, pixel/decoder limits and all primary/backup-copy deletion before activation; no bucket or image processor has been provisioned. See [R2 data location](https://developers.cloudflare.com/r2/reference/data-location/) and [public-access controls](https://developers.cloudflare.com/r2/buckets/public-buckets/).

GDPR/AVG is an explicit delivery requirement (NFR-09). Implement the data-rights workflow alongside task erasure and staff operations, preserving ownership checks and separate finance/evidence schedules; keep the processing inventory, vendor/transfer review and breach runbook aligned with actual runtime behavior. See [the compliance evidence requirements](09-security-privacy-and-trust.md#8-compliance-launch-checklist).

## 4. Company payment to first-publication protocol

Confirmed material-edit rule: a new scope revision refunds any captured payment for an unpublished offer on an obsolete revision; published offers stay visible with a scope-change label and free edits, without automatic refund or extra fee. See [ADR 0005](../docs/adr/0005-version-material-task-scope-changes.md). Serialize material edits through the same job lock as publication, so edit-before-publication refunds and publication-before-edit preserves the published offer with a label. A company must review the current scope before an edited offer can be treated as current; do not silently relabel old offer text as covering the new work. Revision history remains task-scoped content under the original deletion deadline.
Draft offer is free. Fee is server-derived EUR 1.00 gross under fee policy R1; body includes expected material revision and accepted policy version, not an authoritative amount.

1. Authenticate company; validate safe contact/profile/rough offer. Claim actor+operation+idempotency key and canonical payload hash.
2. In job -> response lock order, ensure OPEN, now < delete_at, same material revision, not own task/held account. Find/create unique response row. A WITHDRAWN response rejects a new publication purchase and cannot be replaced with a fresh response row. If already fulfilled and still eligible, return existing result at zero new charge; reopening never creates another fee or restores withdrawal.
3. Reuse an unresolved payment attempt only if its publication generation and material revision remain eligible. Invalidated/unknown attempts require reconciliation, not revival or replacement while unresolved. Create one pending attempt/reference with the current generation/revision and commit. Outside locks, create hosted PSP payment with supported stable idempotency; if outcome unknown, reconcile that attempt before creating another.
4. Persist the Mollie payment ID and checkout URL. Classic webhook input is a bounded form-encoded payment ID, not payment proof; durably queue a verification request for a known local payment, then retrieve its current state with server credentials. See the Mollie mapping below.
5. Fetch payment via authenticated PSP API. Verify merchant/environment, EUR, 100 gross cents and stored attempt reference. Redirect/body-supplied “paid” is not proof.
6. In job -> response -> payment-attempt lock order, evaluate current state/deadline/material revision/publication generation and ensure the attempt has no reserved/pending/completed refund or reversal. If valid and not previously fulfilled, atomically mark offer PUBLISHED, create unique fulfillment/fee journal and minimal outbox event. Receipt is recoverable after timeout.
7. If task closed/deleted/held/materially changed, the attempt's publication generation is obsolete, or another valid attempt already fulfilled, do not publish this payment; create one full-refund obligation. A task reopened before a late callback still cannot validate its old canceled attempt. Never substitute a wallet balance or auto-pay for another task.
8. Repeated callback/return/retry gets the existing result. Reopening a voluntarily closed job before delete_at does not recharge an existing fulfilled response and does not restore prior callback permission. After a definitive refunded failed attempt, a new deliberate reviewed attempt is possible; no two retained successful fees.

All writers, including staff tools, use the same lock order and uniqueness constraints. Close/edit/delete races serialize through the job row. Provider observation can precede a lock; the business decision uses state under that lock. Use bounded deadlock retry with the same operation identity. See [PostgreSQL locking](https://www.postgresql.org/docs/current/explicit-locking.html) and [Mollie payment flow](https://docs.mollie.com/docs/accepting-payments); references do not prove future code correct.

### Mollie implementation mapping (selected provider, not implemented)
- Use the [Payments API](https://docs.mollie.com/reference/create-payment) through a small server-only adapter on the web/worker runtime. Pin a maintained runtime/HTTP client and validate API response shapes during implementation. The current plan does not require a browser/native payment SDK or a particular Node client package.
- Persist an attempt before `POST /v2/payments`; send its stable operation identity as `Idempotency-Key`. The server owns `amount: {currency: "EUR", value: "1.00"}`, a generic fee description, opaque attempt metadata, and configured redirect/webhook URLs. No client task/contact/photo data enters provider descriptions or metadata. Store returned payment ID, mode/profile association and `_links.checkout.href`; use a reviewed HTTPS provider URL and a GET redirect, such as HTTP 303. Parse money exactly into integer cents; no float-based amount comparison.
- Use `POST /api/v1/webhooks/mollie` for classic Payments API notifications. Accept a bounded `application/x-www-form-urlencoded` body containing one payment `id`; treat it as untrusted input. This flow has no signed event envelope or unique provider event ID. Only the later authenticated API read supplies payment facts; no callback body, origin claim or browser return can authorize publication. See [classic webhooks](https://docs.mollie.com/reference/webhooks).
- Look up the ID within the server-configured environment/merchant's local attempts. For a known ID, atomically persist a minimal internal notification/verification request and outbox work, then return 200; inability to durably accept returns 503. Malformed input returns 400; unknown well-formed IDs receive generic 200 without disclosure or arbitrary external fetches. Reconciliation recovers create-timeout cases where a callback arrived before the provider ID was saved. Keep request bounds/rate controls; exempt this exact Mollie notification route from cookie CSRF, not company purchases.
- Classic notifications can repeat the same payment ID for later payment/refund/chargeback changes. Do not deduplicate that ID forever: each accepted notification must schedule or durably refresh verification. Coalescing must preserve notifications arriving during a worker lease. Local fulfillment/refund/journal uniqueness prevents duplicate business effects; an internal notification UUID is not a Mollie event ID.
- Retrieve `GET /v2/payments/{id}` with the configured merchant/profile credentials; validate the recorded ID, owned attempt metadata, `profileId`, `mode`, EUR and exact 100-cent amount. Require `status: paid` with sufficient unreversed/unrefunded funds and no local refund reservation before publication. `open`, `pending`, `authorized`, failed/canceled/expired states and redirect appearance cannot fulfill. Read associated refunds/chargebacks when needed; a payment can remain paid while refund state changes. See [payment retrieval](https://docs.mollie.com/reference/get-payment) and [statuses](https://docs.mollie.com/docs/handling-payment-status).
- The confirmed method scope is iDEAL/Wero and cards only. Apply a server-maintained allowlist of merchant-approved, validated target methods when creating hosted checkout; a caller or broader dashboard setting cannot expand it. Keep each target disabled until €1 payment, full-refund and phone/PWA return tests pass. Validate the retrieved payment's actual method before fulfillment; an unsupported-method capture cannot publish and follows the existing paid-unpublished refund workflow.
- Browser return may request the same verification only after owned-attempt authorization. Background reconciliation covers missed notifications and continues refunds after task erasure; no browser visit is required.
- Mollie documents a one-hour `Idempotency-Key` cache tied to the API credential. Store local operation uniqueness, request hash, creation time and a non-secret credential-version reference beyond that window. Expiry or credential rotation does not authorize a new create: retrieve known objects or reconcile recent merchant records by opaque attempt metadata, escalating unresolved ambiguity. See [idempotency guidance](https://docs.mollie.com/reference/api-idempotency). Preserve the same intent and payload on an allowed retry; never let automatic client retries create a replacement after safety conditions change.

## 5. Refund/accounting recovery
Use separate payment, publication and refund states. A captured payment is not earned income until the offer is fulfilled. A valid visible offer later losing work/no reply/client closure is not automatically refundable: the platform cannot observe private calls or construction success.

For failed publication/system duplicate/confirmed invalid listing under R1, reserve a unique refund amount <= captured less prior refund/reversal before calling PSP. Submit with stable attempt identity; verify provider result. Unknown timeout stays pending, not released then resent. Late payment/extra capture routes to refund rather than a second fulfillment. Chargebacks are separately recorded and reconciled; no silent negative wallet because there is no MVP wallet.

Confirmed incident policy: authorized staff approval of a substantiated fake, duplicate or materially misrepresented task creates a full €1 refund obligation, bounded by funds already returned/reversed so the principal is never repaid twice. Record the case, decision/reason and necessary evidence separately from ordinary task content. Seven days from payment is a reporting target, not a request-validation cutoff; credible later evidence still reaches review. Incident refunds preserve historical fulfillment and terminal withdrawal, and cannot reset payment uniqueness or authorize another publication.

Confirmed submission target: automatically submit verified failed-publication/duplicate-capture refunds and submit confirmed refunds to Mollie within one business day of verification or staff approval. Persist that original timestamp and the computed submission deadline; retries, duplicate approval, worker restart or provider timeout cannot restart the clock. Record submission attempts, authenticated provider acceptance and completion separately. Escalate overdue, queued or failed obligations while preserving unknown-result reconciliation and refund reservations. Configure/document the operating calendar and timezone before paid beta; provider completion and bank arrival are separate from this platform target.

For Mollie, create a refund under the recorded payment using `POST /v2/payments/{paymentId}/refunds` and a stable refund-obligation `Idempotency-Key`; store the returned refund ID separately. Retrieve/list refunds and chargebacks during notification processing and scheduled reconciliation. `queued`, `pending` and `processing` are not completed refunds; only an authenticated `refunded` result completes the obligation. Queued refunds may need merchant balance funding; failed/canceled results require an accountable exception workflow. After an ambiguous creation timeout, keep the reservation and inspect existing provider refunds before any resend, including after the one-hour cache window or credential change. Classic callbacks cover some refund transitions, so polling must also cover states without callbacks. See [refund lifecycle/recovery](https://docs.mollie.com/docs/refunds), [create refund](https://docs.mollie.com/reference/create-refund) and [retrieve refund](https://docs.mollie.com/reference/get-refund). Confirm method refund limits and the operational policy before live charging.

Journal is append-only with unique effect references and balancing controls. Keep minimum company/payment/invoice/time/opaque task-reference evidence; no photos, raw client contact or rough-offer body in long-lived PSP metadata/finance logs. Accountant approves VAT/tax point/invoice corrections and legal retention.

## 6. Region and radius matching
Normalize Dutch postcode/city and validate membership in the confirmed pilot region: the whole provinces of Groningen and Fryslân, including Drachten. Use a validated postcode/municipality-to-province mapping. Company-selected radius controls matching but never expands task-publication eligibility beyond those two provinces.

Use provider-returned/licensed coarse postcode-area or city centroid coordinates, and explicit CRS transformation to WGS84 where needed. Match category + company radius using geodesic/straight-line distance (e.g. Haversine); label it approximate, not driving distance. Suggested radius options 10/25/50/100 km, with a proposed 1–200 km validated range. The company controls radius; no GPS permission is required.

PDOK Location API is confirmed on 22 October for Dutch location lookup. Use a server-only adapter with the minimum postcode/city query; do not send names, email, phone, task text, guest credentials or user identifiers to PDOK. Calculate approximate category/radius matches in our application/database and retain only necessary location fields under their existing task/company retention schedules. Exact coordinates stay out of company task projections and notifications. Provider request logging, terms and retention remain part of NFR-09 review; public location data does not make the linked task location anonymous.

The current [PDOK introduction](https://www.pdok.nl/location-api1) points to the [Location API specification](https://api.pdok.nl/kadaster/location-api/v1/api). Qualify exact endpoints/collections, coordinate metadata, attribution/data-use terms, limits and a permitted coarse-location strategy; do not assume legacy Locatieserver endpoints or a complete postcode-centroid dataset. Validate postcode/city/province consistency, ambiguous matches and border cases across the whole confirmed pilot. Missing/ambiguous results keep the task in draft with a clear retry/correction path until eligibility is established; do not fabricate coordinates, silently choose an unrelated address or automatically send queries to another provider. Google remains unselected comparison context.

## 7. Opt-in task email notifications
On task publication or eligible material revision, enqueue minimal matching work. A confirmed subscribed company receives safe category/city/PC4/timing metadata and an authenticated link, not photos, full postcode, client contacts or guest tokens. Do not send the full post to arbitrary SME email lists.

Confirmed cadence: explicit subscribers default to one daily digest, with optional instant emails and editable/unsubscribe settings. Store category/radius/frequency/locale preferences and consent evidence separately; frequency selection or account creation cannot activate subscription. Suppress empty digests. Instant mode uses queued event delivery rather than a guaranteed arrival time.

Use a unique company+job+revision+notification-kind delivery identity, with frequency kept outside that identity. Digest and instant scheduling must share delivery history so switching modes cannot resend an already delivered event or create two logical deliveries. At dispatch recheck current frequency, task OPEN/not expired/not held, company active, match and subscription; reschedule eligible unsent work for the current mode and suppress unsubscribed/closed/ineligible work. Use bounded retries, delivery status and bounce suppression. External accepted email cannot be recalled; no job body in it limits residual exposure.

## 8. Three-calendar-month deletion
Confirmed policy: task content expires three calendar months after first task publication to companies, with no extension by later activity and with month-end clamping; see [ADR 0004](../docs/adr/0004-expire-tasks-from-first-publication.md). Neither draft creation nor paid offer publication starts this clock. Proposed technical mapping: compute immutable delete_at from task first_published_at in Europe/Amsterdam, add three calendar months, clamp month-end to the last valid date and convert to UTC. A 31 January publication expires 30 April at the corresponding local time. Proposed DST rule: shift a nonexistent target local time forward by the clock-change gap; for a repeated local time choose the earlier instant. Store the resolved deadline once, show it before posting and test both cases. Finalize and validate the timezone/DST details alongside the retention wording. Live purge within 24h, isolated backup roll-off within 30 days and narrow separate billing/active-company/case-evidence retention are confirmed; exact exception schedules receive professional review.

At delete_at authorization immediately denies all task reads/writes/downloads/contact/notifications. Idempotent worker marks inaccessible, revokes sessions/tokens/grants, removes response text/contact snapshots and task location, then deletes originals/variants/quarantine/object versions and any search/cache/provider copies permitted under contracts. Confirmed live-store completion <=24h; failed deletes retry with alerts and per-target progress. Keep only minimal tombstone/reference needed for deletion and separately justified purposes.

A new offer, close/reopen or optional account creation never moves delete_at. No deletion job payload may contain the content being deleted. Confirmed rolling backup limit is <=30 days, covering database/PITR and media backups; validate provider settings and any secondary copies. Before restore opens, reapply tombstones and deadline filters using deletion records that remain available independently of the restored snapshot. Confirmed evidence-hold boundary: strictly necessary material for a named case, restricted access and a review/deletion date. Ordinary task records still expire and purge on schedule; any preserved case evidence has its own reviewed purpose/fields/schedule and never reopens task or callback access. Active company settings and minimum billing records also use separate reviewed schedules without retaining old task content.

## 9. Media, PWA and observability
Confirmed on 22 October: up to six photos per task and 10 MB per file. Enforce count and actual byte limits server-side across individual/batch/concurrent uploads, including in-flight reservations; a browser check or declared Content-Length alone is insufficient. Proposed technical mapping uses a 10,000,000-byte cap, atomic task-scoped slot reservations and idempotent upload completion; retries do not allocate extra slots, and cleanup releases failed/removed attachments safely. Stream bounded input rather than buffering a whole batch in Worker memory. Pixel/decoder limits remain qualification work independently of compressed file size.

Confirmed on 22 October: accept JPEG, PNG, WebP and iPhone HEIC photo inputs and convert them to sanitized JPEG/WebP for display. Real type/decoder checks determine acceptance, not file extensions or browser MIME assertions. Qualify actual HEIC fixtures as well as iPhone file-picker/camera behavior, orientation/color handling and metadata removal. This confirms the format requirement, not universal support for every HEIF codec, animated image or Live Photo/video component; unsupported/corrupt inputs need explicit errors. The founder subsequently selected Cloudflare Images through its Workers binding for this conversion; no binding, paid plan or other resource has been provisioned.

Confirmed processor decision on 22 October: use the [Cloudflare Images Workers binding](https://developers.cloudflare.com/images/optimization/binding/) for upload-time conversion. It accepts raw image streams from private storage without a public source URL, and Cloudflare provides a [transform-to-R2 tutorial](https://developers.cloudflare.com/images/tutorials/optimize-user-uploaded-image/). Proposed flow: reserve the upload slot, store bounded input in private quarantine, enqueue durable PostgreSQL processing work, inspect/decode and transcode through the binding, persist validated JPEG/WebP variants in EU R2, then conditionally mark the attachment ready after rechecking the task/attachment state and expiry. Resumable jobs and source/version identity prevent replay from creating a second attachment; deletion during processing must remove late/orphan output rather than restore access. Quarantine cleanup remains bounded and must be specified/qualified.

Serve persisted sanitized variants through authorized Worker reads rather than transforming on every view. The binding documentation states responses are not automatically cached; do not copy its optional public-cache example or introduce public transformation/original-fallback URLs. [Cloudflare format/limit documentation](https://developers.cloudflare.com/images/get-started/limits/) lists HEIC input and a 20 MB binding input ceiling, while the platform keeps its stricter confirmed 10 MB cap. These are provider capabilities, not a successful application test.

Before live processing, qualify pixel/decoder and output limits, metadata removal for both outputs, source/orphan cleanup, interrupted/concurrent jobs and all four input formats in the actual deployed runtime. The [metadata controls](https://developers.cloudflare.com/images/optimization/features/#metadata) document a JPEG default that preserves a copyright tag; use and verify explicit full removal or a validated equivalent through the chosen binding API, including GPS/other identifying metadata, while applying orientation/color correctly. R2 EU placement does not establish Images processing/log/temporary-copy locations: include this service in NFR-09 contract/subprocessor/transfer and retention review before personal photos enter it. The [current Images pricing](https://developers.cloudflare.com/images/pricing/) includes a monthly free allowance and paid transformation usage; exact plan, billing controls and total Workers/R2 costs remain budget work. The processor choice is confirmed; runtime/GDPR readiness is not yet established; no binding, paid plan or cloud resource has been created.

Require real-type checks, quarantine/scan, EXIF removal, sanitized preview and clear processing/unsupported-format errors. Metadata stripping cannot guarantee every picture lacks an address/face: client preview and report/remove path remain necessary. Worker reads enforce current permissions and delete_at on every request; no public bucket URLs or prior download URL may bypass those checks.
