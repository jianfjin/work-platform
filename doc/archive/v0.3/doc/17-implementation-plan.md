# Implementation plan

**Status:** implementation plan approved by the founder on 22 October 2026; runtime qualification is the first implementation milestone, with runtime and launch evidence pending. **Updated:** 22 October 2026.

## Settled rules

The existing requirements establish free client use, private rough offers, client-controlled direct contact, no commercial three-company cap, and Dutch/English Web/PWA delivery. The founder has now confirmed €1.00 including VAT per company/task for the first successfully published private rough offer: reading and edits are free, a reply is not guaranteed, and failed publication receives a full refund. See [ADR 0001](../docs/adr/0001-charge-for-first-offer-publication.md) and the [glossary](../CONTEXT.md).

Collection is confirmed as individual Mollie-hosted checkout for each €1 publication fee, accepting per-payment checkout friction and processing costs to avoid upfront commitments/prepaid accounting. Mollie was explicitly selected as the sole provider for this stage on 22 October, without alternative/fallback evaluation; see [ADR 0007](../docs/adr/0007-use-mollie-for-current-payment-integration.md). Method scope is confirmed as iDEAL/Wero and cards only. Each method requires merchant approval and successful €1 payment, full-refund and phone/PWA return tests before activation. Bundles, wallets and subscriptions are deferred until after MVP; live merchant/method activation remains launch work.

Incident-refund eligibility and reporting are confirmed: a substantiated fake, duplicate or materially misrepresented task qualifies for a full €1 refund, with a seven-day reporting target from payment while credible later evidence is still reviewed. Staff record the approval/reason and only necessary case evidence; no reply or losing the work alone remains non-refundable. Refunds preserve publication history and terminal withdrawal. Submission timing is confirmed: automatically submit verified failed-publication/duplicate-capture refunds, target submission to Mollie within one business day of verification or staff approval, and escalate overdue, queued or failed obligations. Track submission and completion separately without resetting the deadline on retries; bank arrival is not promised by this target. See [payment policy](08-payments-and-economics.md).

The founder also confirmed the whole provinces of Groningen and Fryslân, including Drachten, as the pilot region. Company-selected service radii control matching within this task-publication area; postcode/municipality mapping must be validated during implementation.

Task-alert frequency is confirmed: companies explicitly opt in, with one daily digest as the default and optional instant emails. Keep category/radius matching, confirmed recipients, editable settings and easy unsubscribe. A frequency choice alone does not subscribe a company. Both modes recheck live task/company/subscription eligibility before dispatch, and switching modes cannot create a second logical delivery of an already sent event. See [operations](15-operations-and-growth.md).

Background jobs are confirmed as durable PostgreSQL inbox/outbox/jobs with bounded Cloudflare Cron handlers, initially polling every minute for due work/retries/reconciliation. Optional bounded immediate attempts follow durable commit and use the same claims; interruption must leave recoverable work. Qualify leases, idempotency/provider ambiguity, priority/fairness and backlog capacity against refund/purge targets; cadence does not guarantee arrival time. Cloudflare Queues is unselected.

The founder requests Cloudflare app hosting and explicitly confirmed TypeScript on Workers after the delegated performance choice and discussion of possible AI integrations. Hono is confirmed for the backend HTTP API. Expected lower runtime overhead and shared frontend/backend tooling inform the TypeScript choice, without claiming a measured performance win. Paid Render PostgreSQL in Frankfurt is confirmed, accessed through Hyperdrive with application query caching disabled. React Router framework mode with React/Vite/SSR is confirmed for the frontend; see [ADR 0010](../docs/adr/0010-use-react-router-for-web-pwa.md). Drizzle ORM with node-postgres (pg), typed schema/queries and reviewed SQL migrations is confirmed; explicit SQL locks and database constraints remain authoritative for critical effects. Better Auth with account/session records in Render PostgreSQL is confirmed; see [ADR 0011](../docs/adr/0011-use-better-auth-for-company-and-staff-accounts.md). Company verified-email/password sign-in, email verification and password recovery are confirmed. Invite-only staff email/password with mandatory authenticator-app TOTP and one-use recovery codes is confirmed, preserving MFA through password recovery. Exact package versions, staff provisioning/exceptional-recovery procedures, database compute/storage/version, job/media configuration and provisioning remain open. Resend is confirmed for direct platform email with application-specific credentials and a dedicated sending subdomain; the parent domain, subdomain label, sender/Reply-To addresses and plan remain open; see [ADR 0012](../docs/adr/0012-use-resend-for-platform-email.md). See [ADR 0008](../docs/adr/0008-use-typescript-for-cloudflare-backend.md), [database ADR 0009](../docs/adr/0009-use-render-postgresql-in-frankfurt.md), [Cloudflare versus Render](18-cloudflare-vs-render.md) and [backend assessment](19-backend-options.md).

PDOK Location API is confirmed on 22 October for Dutch location lookup, with minimum server-side queries and approximate radius matching in our application/database. Qualify the current API/datasets, source terms/CRS/limits, coarse-location and province accuracy, and the GDPR data flow; no external task/contact payloads or automatic alternative-provider queries.

Private Cloudflare R2 photo storage with explicit EU jurisdiction and authorized Worker reads is confirmed on 22 October. Confirmed photo inputs are JPEG/PNG/WebP and iPhone HEIC, converted to sanitized JPEG/WebP for display through the confirmed Cloudflare Images Workers binding at upload time. Uploads are optional, limited to six photos per task and 10 MB per photo; enforce count/bytes server-side, including concurrent in-flight uploads. Keep public bucket access disabled and enforce current access/expiry on every photo read; image sanitization, exact configuration and complete erasure remain qualification work. The founder also explicitly requires GDPR/AVG compliance throughout the project, tracked as NFR-09. Deliver the [privacy evidence requirements](09-security-privacy-and-trust.md#8-compliance-launch-checklist) before real personal-data use, including purpose/data-flow records, notices and rights handling, vendor contracts/transfers, DPIA/DPO screening and breach readiness. EU storage alone does not establish compliance, and Resend US account-data processing still requires review.

Guest tasks stay unpublished until email confirmation. Short-lived email links provide access scoped to one task, with fresh-link recovery. Optional client accounts, multi-task account dashboards and task linking are confirmed deferred until after MVP; company/staff accounts remain in scope. See [ADR 0002](../docs/adr/0002-confirm-email-for-guest-task-ownership.md). Exact security lifetimes remain implementation choices; Resend is the confirmed mail provider.

Client contacts remain private by default. Explicit opt-in shares selected email/phone fields with every eligible published responder while the task is open, without individual company selection or a fixed audience cap. Revocation or closure stops future disclosure; copied details cannot be recalled. See [ADR 0003](../docs/adr/0003-client-controlled-responder-contact.md).

Material task edits create a new scope revision. Captured payments for unpublished old-scope offers receive a full refund; already published offers remain visible with a scope-change label and free edits, without automatic refund or extra fee. Publication/edit ordering determines the outcome; see [ADR 0005](../docs/adr/0005-version-material-task-scope-changes.md).

Voluntarily closed tasks may reopen before original expiry, retaining offers/fees without another fee for previously published companies. Client contacts reset to private until fresh callback opt-in, and canceled payment attempts never revive. Persist attempt invalidation independently of current OPEN state so a late old capture refunds even after reopening; see [ADR 0006](../docs/adr/0006-reopen-without-renewing-fees-or-consent.md).

Published-offer withdrawal is final for that company/task in MVP. Client projections return company name and withdrawn marker only, omitting offer text/website/company contacts; callback access ends, the original fee remains without automatic refund, and no restoration/republishing/new checkout is allowed, including through task reopening or old payment events. See the same [lifecycle ADR](../docs/adr/0006-reopen-without-renewing-fees-or-consent.md).

Task content expires three calendar months after the task first becomes visible to companies, with month-end clamping such as 31 January to 30 April. Later activity never renews the clock, and paid offer publication is independent. Confirmed: access ends immediately at expiry, ordinary live task data and all photo/object versions are purged within 24h, isolated backups age out within 30 days, and restores reapply deletions before serving users. Narrow separate retention is confirmed for minimum billing records, active company/alert settings and strictly necessary case evidence; holds need a named case, restricted access and a review/deletion date. Exact exception purposes/fields/schedules receive accountant/legal review before launch; see [ADR 0004](../docs/adr/0004-expire-tasks-from-first-publication.md).

Other recommendations in the source documents retain their stated proposed status. This plan consolidates the confirmed decisions into implementation work and launch gates; no application or infrastructure has been created.

## First implementation milestone: runtime qualification

Use synthetic data and provider test mode to produce a small deployed-runtime qualification slice before building the complete flows. Local mocks alone are insufficient; no such implementation or deployment has run yet.

1. Pin compatible Workers/Hono/React Router/Drizzle/pg/Better Auth versions; establish build, test configuration, reviewed SQL migrations and isolated credentials. Prove SSR/API/session integration and real PostgreSQL transaction commit/rollback through cache-disabled Hyperdrive.
2. Exercise representative ownership/consent reads and concurrent publication/outbox or job claims on independent database connections. Demonstrate rollback, lock/constraint behavior, immediate-attempt versus Cron races, lease takeover and recovery after interruption.
3. Prove Mollie classic known-payment intake can durably schedule authenticated verification, including commit failure/replay and the local attempt/reference mapping; keep actual payments in test mode. Qualify Resend send/event contracts with stable identities, raw-body signature verification, suppression and token-safe delivery storage.
4. Process JPEG/PNG/WebP and real HEIC fixtures through the Images binding into private EU R2 variants. Verify actual output metadata/orientation, byte/pixel limits, authorized reads and task deletion during processing; retain a bounded cleanup path for source/orphan objects.
5. Record representative route timings, job backlog behavior, connection/runtime limits and actual proposed service costs against the €100/month budget. Verify recovery features/retention settings and identify evidence still needed for the full restore drill. Re-estimate the remaining slices from these results before scheduling them.

Completion is a reproducible qualification report with configuration/versions, passing focused runtime evidence, current costs and any blocking incompatibility. The full NFR-03 load target, deletion-safe financial restore and release acceptance suite remain later qualification; no partial spike is a passing production result. If a confirmed constraint cannot be met, record the specific conflict and resolve it before dependent work or live use.

## Architecture and hosting

The proposed backend is a modular monolith whose TypeScript API and job entrypoints share domain/database rules on Workers. Python, Go and Rust remain assessed alternatives rather than parallel MVP backend implementations; see [backend assessment](19-backend-options.md). PostgreSQL remains an external managed EU service. Frontend deployment/framework selection does not split task/offer/billing modules into independent services.

Render Frankfurt with persistent web/worker processes and colocated PostgreSQL is retained as the comparison baseline. Cloudflare is the founder's requested app host. The [comparison](18-cloudflare-vs-render.md) recommends a first foundation qualification slice covering the framework build, identity, PostgreSQL transactions without stale query caching, durable Mollie intake, resumable scheduled work and private image handling. No such spike or deployment has run.

Paid Render PostgreSQL in Frankfurt is confirmed; Supabase remains comparison context. Hyperdrive uses Render's external TLS hostname with reviewed Cloudflare source-IP restrictions and server-only credentials. Review processing and backup locations, exact compute/storage/version, and complete recovery-qualified pricing. Paid PITR does not itself prove the existing <=1h recovery-point/<=4h restoration targets or deletion-safe recovery. Actual costs, runtime qualification and restore/retention evidence remain implementation and launch work; nothing has been provisioned.
